Production Backend: Domain Logic, Not Controller Spaghetti

The biggest backend mistake is coupling transport layer and business rules. Separate API contracts, application services, domain model, and persistence adapters.

4.1 Clean Layering Blueprint

  • Controller: input validation and response mapping.
  • Application service: orchestrates use-case workflows.
  • Domain: entities, value objects, policies, invariants.
  • Infrastructure: databases, queues, external APIs.

4.2 Example Spring API Slice

@RestController
@RequestMapping("/api/orders")
class OrderController {
    private final CreateOrderService createOrderService;

    OrderController(CreateOrderService createOrderService) {
        this.createOrderService = createOrderService;
    }

    @PostMapping
    ResponseEntity<OrderResponse> create(@RequestBody @Valid CreateOrderRequest request) {
        var result = createOrderService.execute(request.customerId(), request.lines());
        return ResponseEntity.status(HttpStatus.CREATED).body(OrderResponse.from(result));
    }
}

Notice what is absent: no repository logic in the controller.

4.3 Persistence Strategy

  • Transactional commands: JPA or JDBC with explicit boundaries.
  • Read-heavy queries: projections, read models, or SQL-first approach.
  • Use outbox pattern for reliable event publication.
@Transactional
public Order createOrder(CreateOrderCommand cmd) {
    Order order = Order.create(cmd.customerId(), cmd.lines());
    orderRepository.save(order);
    outboxRepository.enqueue("order.created", order.id().toString(), order.toJson());
    return order;
}

4.4 Security Baseline

  • OAuth2/OIDC for identity delegation.
  • JWT validation + authorization by role/permission.
  • Input validation and output encoding for trust boundaries.
  • Rate limits + audit logs for sensitive operations.

4.5 Async and Messaging

@KafkaListener(topics = "payment-events", groupId = "billing")
public void consume(PaymentEvent event) {
    switch (event.type()) {
        case "PAYMENT_CONFIRMED" -> billingService.markPaid(event.orderId());
        case "PAYMENT_FAILED" -> billingService.markFailed(event.orderId(), event.reason());
        default -> throw new IllegalStateException("Unknown event type");
    }
}

Design consumers as idempotent handlers: same message can be processed more than once safely.
