Theory Drives Delivery Quality

Without architecture theory, teams overfit to local optimizations and produce fragile systems. This chapter teaches decision frameworks: coupling/cohesion, bounded contexts, consistency models, trade-off economics, and socio-technical design.

8.1 SOLID, But Applied with Context

  • S: organize by behavior and policy, not by framework annotations.
  • O: prefer composable strategies and extension points.
  • L: enforce substitutability in contracts and tests.
  • I: avoid interface inflation; split by client need.
  • D: point business policies inward; infrastructure outward.

8.2 Architecture Patterns Decision Guide

Layered

Simple domains, small teams, fast onboarding.

Hexagonal

Need portability across adapters and explicit boundaries.

Modular Monolith

High cohesion with operational simplicity.

Microservices

Only when team topology and domain scale justify distributed complexity.

8.3 Domain-Driven Design Core

  • Bounded context defines language and model ownership.
  • Aggregate enforces transaction consistency boundary.
  • Domain events express meaningful state transitions.
public final class OrderAggregate {
    private final OrderId id;
    private OrderStatus status;

    public List<DomainEvent> confirmPayment(PaymentId paymentId) {
        if (status != OrderStatus.PENDING_PAYMENT) {
            throw new IllegalStateException("Order cannot be paid in state " + status);
        }
        status = OrderStatus.PAID;
        return List.of(new OrderPaid(id, paymentId));
    }
}

8.4 Distributed Systems Theory in Practice

  1. Consistency model: strong vs eventual consistency by user impact.
  2. Failure model: assume partial failures and retries.
  3. Observability model: metrics, logs, traces from day one.
  4. Cost model: optimize for total cost of ownership, not local performance only.

8.5 Design Review Rubric

  • What business invariant is protected by this design?
  • What are the failure modes and fallback paths?
  • How observable is this component in production?
  • Can another team safely evolve this API?
  • What is the migration path if assumptions change?

8.6 Quality Attributes and Trade-Offs

Architecture is optimization under constraints. Improving one quality attribute often costs another.

  • Latency vs consistency: stronger consistency can increase response time.
  • Throughput vs debuggability: asynchronous pipelines can reduce transparency.
  • Modularity vs performance: extra boundaries can add serialization and network cost.
  • Security vs developer speed: stricter controls require more process discipline.

8.7 CAP/PACELC Decision Lens

In distributed systems, trade-offs are unavoidable. Use CAP/PACELC as a thinking framework, not a slogan.

  1. CAP event: if partition happens, choose consistency or availability by business criticality.
  2. PACELC normal mode: even without partition, choose between latency and consistency.
  3. Document your choice with user-impact examples and rollback strategy.

8.8 ADR Template (Architecture Decision Record)

# ADR-007: Choose Modular Monolith for Commerce Core

## Status
Accepted

## Context
Team size is 9 engineers. Domain boundaries are still evolving.

## Decision
Implement modular monolith with strict package boundaries and event-based module integration.

## Consequences
Positive: simpler deployment and easier debugging.
Negative: requires discipline to avoid accidental coupling.

Strong architecture teams write ADRs continuously and revisit them when assumptions change.
