Performance Engineering Is a Method, Not a JVM Flag List

Java performance quality depends on modeling allocations, understanding GC pressure, avoiding accidental contention, and observing with metrics. Blind tuning creates regressions.

3.1 JVM Memory Areas

  • Heap: object allocation and garbage collection.
  • Stack: call frames, local variables, references.
  • Metaspace: class metadata (native memory).
  • Code cache: JIT-compiled machine code.

Latency spikes usually map to allocation bursts, lock contention, or external IO stalls.

3.2 Garbage Collectors

G1

General purpose, balanced default for many services.

ZGC

Ultra-low pause goals for large heaps and latency-sensitive systems.

Shenandoah

Low-pause alternative with concurrent compaction focus.

3.3 Practical Profiling Workflow

  1. Set SLO/SLA targets first: p95, p99, throughput, error rate.
  2. Collect baseline metrics under representative load.
  3. Use async-profiler/JFR for CPU and allocation hotspots.
  4. Change one variable at a time and compare.
// Example: allocation-aware data transform
public List<String> normalized(List<String> input) {
    return input.stream()
        .map(String::trim)
        .filter(s -> !s.isEmpty())
        .map(String::toLowerCase)
        .toList();
}

3.4 Concurrency Hazards

  • Race conditions from mutable shared objects.
  • Thread pool starvation when tasks block unexpectedly.
  • False sharing and cache-line contention in hot loops.
private final ConcurrentHashMap<String, LongAdder> counters = new ConcurrentHashMap<>();

public void mark(String key) {
    counters.computeIfAbsent(key, k -> new LongAdder()).increment();
}

Choose lock-free or contention-friendly structures before adding more threads.

3.5 High-Impact JVM Flags (Start Conservatively)

java -XX:+UseZGC -XX:MaxRAMPercentage=70 -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/tmp -Xlog:gc*:file=gc.log:time,uptime,level,tags \
     -jar app.jar

Always validate with load tests. Correct architecture beats aggressive flags.
